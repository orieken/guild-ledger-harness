# Guild Ledger H2 treatment

Draft 0.1.0, 21 October 2026. This repository versions the treatment package, not application code. No rules are installed globally or discovered automatically. The research supervisor copies only `package/` into a disposable runner's explicit read-only treatment input.

Manifest SHA-256: `f5b160533d307fcd627080d4dc5555b71d2fdc53453ea56de2b3de644d18c5a6`

H2 contains the exact H1 guideline bytes plus a bounded implementation → fresh review → optional single repair workflow.

The manifest declares every asset hash, ordered stage instructions and stage limits. Adding tools, skills or task-specific facts requires a new reviewed profile. Shared task mechanics, prompt completeness, base tools, runtime/model/auth and aggregate allowances belong to the campaign and remain fixed across treatments.

The current container adapter supports hash verification and initial-stage prompt assembly with a fake CLI only. It does not execute a real multi-stage workflow. A production H2 supervisor must enforce fresh sessions, read-only review copies, structured verdict validation, conditional single repair, aggregate limits, stage lineage and independent final evaluation. An invalid review stops as `invalid-review`; no repair is silently substituted. Human gates yield `needs-human`, not invented approval. Native provider retries and all stage usage count in the same attempt.

Guideline provenance: the H1 package in `orieken/guild-ledger-guidelines` is canonical; H2 vendors identical bytes with the same asset hash. Change them together through an explicit treatment revision, not silently during a campaign. No model calls or campaign admission are authorized by this package.
